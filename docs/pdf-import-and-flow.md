# PDF importing, application analytics, and LiveContainer OAuth

Implemented in the existing Next.js app. No deployment or production SQL execution was performed. Existing migrations, authentication checks, native sources, and Capacitor plugins are preserved. No IPA was built or exported.

## Row alignment and bulk eligibility repair

This follow-up changes only `src/lib/pdf/tracker.ts`, `src/components/pdf-tracker-import.tsx`, `tests/bulk-import.test.ts`, `tests/e2e/import-flow.spec.ts`, `tests/helpers/job-pdf.mjs`, and this guide. It adds no migration, authentication/OAuth changes, native changes, dependencies, or IPA build. Deploy the updated web app through the existing Vercel workflow; migration `003` must already be installed from the original feature, but no new SQL or redirect configuration is needed for this repair.

The coordinate extractor was already available, but the row assembler classified cells from heading text starts and immediately consumed each baseline. Centered date/status values could start to the left of those headings, and metadata printed above a title could be discarded before a row existed. A synthetic PDF reproduced the reported combination of truncated text plus falsely missing date/status. PDF.js also inserts spaces between date fragments, such as `11/10/ 26`. The real two Handshake exports are not in this repository and were requested; no claim of verification against those files is made.

The repaired assembler recognizes wrapped/multiword headers, assigns compact metadata within its column neighborhood, builds shared company/role row bands, and then associates all five columns with those bands. It retains source text and normalizes explicit dates after joining fragments. Navigation, pagination, repeated headers and footers do not become applications. Regression PDFs exercise shifted columns, different cell baselines, wrapped headers, multiple pages, missing cells, and all requested status labels. Closed/Declined remain unresolved for user review; neither becomes Rejected automatically.

Truncated company/title/location values are nonblocking warnings in a compact expandable indicator. Warnings are recomputed after edits. Missing/invalid essentials are row-specific blocking errors; a value containing only ellipsis/punctuation is not an identifiable company/title. Import Selected submits only eligible, explicitly confirmed selections and leaves invalid/unconfirmed rows selected for correction, with a reason for each skipped row. Select All, Deselect All, Select all valid rows, Skip duplicates, Needs attention, per-row eligibility, and confirmation for selected eligible rows use the existing interface styles. Because the existing database requires a supported job type, users can explicitly apply one type to selected rows; no type is inferred.

Requests use the unchanged authenticated import endpoint and transaction RPC, in chunks of 20 to report actual completed-row progress. Successful rows are deselected as results arrive; a later chunk failure retains pending selections and earlier results. Retrying relies on the existing receipts and semantic duplicate checks. Workspace reload refreshes the dashboard and Sankey counts, including after a partial request failure.

## Root causes and schema findings

The old PDF importer flattened text from all pages, ran single-job field heuristics, and produced one job draft. It had no tracker table parser, application row collection, multi-file input, bulk review, or application import endpoint. Flattening discarded column positions, so table cells, repeated page headings, and navigation could not be reliably associated with application rows. A tracker could only reach the individual job creation flow. Its 19,000-character description limit also rejected longer trackers.

The repository schema is the initial `202611110001_initial.sql` plus `002_application_tracking.sql`. These define private company/job ownership, application attempts, one active application per linked job, `applied_on`, and structured status events. `save_tracking_application` already atomically creates company/job/application/bookmark records; its trigger records creation and subsequent status changes. The existing trigger defaults a missing submitted application date to today. Bulk importing therefore requires an actual date before confirmation, rather than allowing that default to invent an imported date.

Only the checked-in schema and its execution in local PostgreSQL/PGlite were inspectable. Deployed schema drift and live Supabase persistence remain unverified without a signed-in test-user token. The only repository PDF fixtures supplied were synthetic encrypted documents; no real Handshake tracker export or Sankey reference image was available in this workspace. Tracker compatibility is tested with positioned browser-print-style synthetic PDFs and still needs verification against the user's actual exports.

## Extraction and review

Discover → **Import PDF** offers **Individual job posting** and **Application tracker / bulk import**.

Individual mode retains the editable company/title/location/type/deadline/salary/URL/description review and the existing job CRUD transaction. Save & start application opens the ordinary application editor. Nothing is saved during extraction.

Tracker mode uses PDF.js selectable text with each item's page, x/y coordinates, width, and height. The parser detects column neighborhoods from company/employer, role/job/title, date-applied, location, and status headings, reconstructs shared geometric row bands, and assigns wrapped cells and offset metadata to them across every page. Repeated headings refresh column positions. Known navigation, page numbers, footer URLs, and inactive-listing labels are excluded from application identities. Inactive listings produce a warning rather than rejection. Unsupported table layouts produce an actionable empty result, not fabricated applications.

Visible ellipses remain in company/title/location fields and produce nonblocking informational warnings. Dates without a year, missing dates, and invalid dates remain blank. No employer, role, year, or application date is inferred. Supported explicit dates are ISO, month-name/day/four-digit-year, and US numeric month/day/two- or four-digit-year. Short numeric years `00`–`99` are interpreted explicitly as `2000`–`2099`; `11/10/26` becomes `2026-11-10`, independent of the current date. Unsupported date formats require correction. Unusual layouts, combined company/role columns, scans, and rows split across page boundaries may require a different export or manual entry.

The horizontally scrollable review table provides company, job title, date applied, location, original and mapped status, job type, existing job selection/application duplicate match, warnings, include/exclude, per-row review confirmation, and removal. Editing a field clears its review confirmation. Users must select a schema-supported job type; missing employment types are not invented. Select all valid rows and Skip duplicates operate on the current edits. Totals show detected, valid, duplicate, invalid, and selected rows. Repeated identical files within one selection are consolidated by their row identities.

Truncation warnings update after corrections and never require the visible text to be expanded. Confirming review acknowledges the selected values and status mapping. Invalid/unconfirmed selected rows are retained with row-specific reasons while eligible confirmed rows import; invalid records submitted directly to the API also return row-specific errors.

Limits: 10 PDFs/session, 10 MiB/file, 50 MiB/session, 40 pages/file, 500 rows/session, 250,000 extracted tracker characters/file, 15 seconds/parser, 120 seconds/client session. Individual text retains its 19,000-character limit. Files are processed sequentially. A session check precedes extraction. Filename/MIME checks supplement actual PDF signature and PDF.js validation.

PDFs remain in memory on the user's device. No raw PDFs are uploaded or stored. No OCR, rendering, PDF JavaScript/actions, attachments, or URL fetching is invoked. External binary resources are rejected; worker fetching, font loading, WebAssembly, and image decoding are disabled. No private PDF/application contents are logged. Browser workers have bounded input/time/text/pages but no portable hard heap quota.

## Import validation repair

The previous review used the final-save schema on every draft. Empty job types, intentionally unconfirmed `reviewed: false`, and ambiguous source statuses consequently appeared as raw Zod errors. A synthetic positioned PDF reproduced this without extraction failure: `11/10/26` reached normalization but the date parser only accepted four-digit years. The checkbox already used `event.target.checked` and JSON booleans; string serialization was not the cause. Applied casing already normalized, while Saved/Preparing/Ready now also map case-insensitively to the existing exact enum values.

Extraction, editable drafts, and finalized import records now have separate schemas. Drafts permit unknown dates/statuses/types and unconfirmed review. Original source dates remain visible alongside normalized date fields. Missing or impossible dates remain unknown; nothing substitutes today's date. Final validation still requires a valid date, explicit supported job type, known status, and literal boolean `true` for confirmation. The Unknown / Not specified type option remains unsavable until the user chooses a database-supported value. No new SQL migration or nullable database change is needed.

The review separates field completeness from confirmation, shows numbered guidance such as “Row 12: Job type needs confirmation,” and preserves other rows' edits when one changes. Editing a row resets only its confirmation. Confirmation serializes the validated final record rather than the entire draft. The API returns all validation problems for each affected row and retains the existing authentication, transactional RPC, duplicate handling, initial history, and dashboard refresh.

## Persistence, duplicates, and history

Apply the new incremental **`supabase/migrations/003_bulk_pdf_import.sql`** after `002`. It adds `applications.source_status`, an RLS-protected receipt table, and the security-invoker `import_tracking_application(jsonb)` function. Do not replace or rerun either existing migration.

`POST /api/import/applications` verifies the user with the ordinary Supabase client, enforces same origin, bounds the streamed JSON body to 1 MiB and 500 rows, and validates selected records with Zod. It returns indexed per-row created/duplicate/error results. The route has a 60-second function limit, a 45-second scheduling budget, and bounded RPC requests. Unattempted rows can be retried; a timeout is not evidence that a database write failed.

Each row RPC is one database transaction. It validates required values again, takes a per-user import lock, resolves an accessible existing job or creates the company/job through existing functions, creates the user-owned application and bookmark, records the existing initial status event, preserves `source = Handshake`, saves the original source status and reviewed application date, and writes the receipt. A row failure rolls back its company/job/application/event/receipt together. Successful rows remain saved when another row fails. Imports use no service-role credentials and do not bypass RLS.

A receipt key consists of SHA-256 of the original PDF bytes plus page/row ordinal. The receipt primary key includes the authenticated user. Reimporting identical bytes reuses the original application even after corrections or later rejection/withdrawal. Different exports also match by selected job or case-insensitive trimmed company/title/location plus application date; an active existing application is reused under the existing duplicate rules. A materially different export with changed/truncated identities may need explicit existing-job matching. Receipts and semantic matching are exposed only within the user's workspace for review. Receipts cannot reference another user's application.

Duplicates return the existing record without replacing its details or status. Deleting an application cascades its receipt and history; a later intentional reimport can create it again. The importer does not create a new attempt simply because an earlier imported application was rejected.

Imported rows use the same applications, jobs, events, application dialog, CRUD service, and status controls as manual rows. Notes, important dates, status changes including Assessment/Interview/Offer, deletion, and history remain available. The existing interviews table and ownership checks are unchanged. This change adds no separate assessment/interview/offer subsystem.

Mappings: Applied → Applied; Interviewing/Interview → Interview; Assessment → Assessment; Offered/Offer/Hired → Offer; Rejected → Rejected; Withdrawn → Withdrawn. Hired → Offer is explicitly flagged because the schema has no Hired status. Reviewed, Declined, Closed, Inactive, Unavailable, and unknown statuses require a user-selected mapping. A closed posting never implies rejection, and Reviewed never implies Interview. The original source status remains visible in the application dialog.

## Analytics

Overview's Application Flow now offers two views using authenticated Supabase workspace records:

- **Current Status**: deduplicates application IDs, counts each application once, and draws Total Applications → status → current outcome category. Each layer conserves the same total. The table and SVG tooltips show counts/percentages. Applied rows older than the configurable No Reply threshold are classified for display only. Stored statuses are unchanged; dates, rather than creation timestamps, control the threshold. Outcome categories describe current statuses, not inferred history.
- **Status Transitions**: aggregates distinct recorded event IDs with valid, different before/after statuses. Creation and ordinary-edit events do not become transitions. Repeated/backward moves count as distinct events. A bipartite before/after graph avoids cycles and labels percentages as shares of events rather than applications. Legacy descriptions are never parsed to invent history.

A new Applied import appears immediately in Current Status and contributes zero transitions until a real status change is recorded. Deleting applications removes their events through existing cascades. Ribbons have a 1.5-pixel visual minimum for rare statuses; tooltips and tables retain exact counts. Both diagrams have semantic table alternatives, consistent existing stage colors, counts, native SVG tooltip titles, and horizontal scrolling on narrow displays. The table provides the reliable touch/keyboard alternative to hover tooltips.

## LiveContainer 3.8.0 investigation and implementation

The user reported LiveContainer **3.8.0**. The guest declares `com.internos.mobile` in the checked-in Info.plist and in the compiled simulator app. Existing AppDelegate/SceneDelegate forwarding and App/Browser plugins already handle that callback. A guest IPA's URL declaration does not register its scheme with iOS SpringBoard as an independently installed application. This explains the reported Safari invalid-address error after Google succeeds. The exact installed guest IPA, host IPA, build hash, and physical-device routing could not be inspected here.

Version-specific official sources confirm forwarding support:

- [LiveContainer 3.8.0 UIKit+GuestHooks.m](https://github.com/LiveContainer/LiveContainer/blob/3.8.0/TweakLoader/UIKit%2BGuestHooks.m): `LCDecodedURLStringFromControlURL` decodes base64 `url`; `LCHandleControlAppURL` handles `open-url` and replaces the incoming URL for AppDelegate/SceneDelegate delivery. This is source verification, not a device-success claim.
- [LiveContainer 3.8.0 LCSharedUtils.m](https://github.com/LiveContainer/LiveContainer/blob/3.8.0/LiveContainer/LCSharedUtils.m): `lcUnorderedUrlSchemes` explicitly lists `livecontainer`, `livecontainer2`, and `livecontainer3`.
- [Official LiveContainer FAQ](https://github.com/LiveContainer/livecontainer.github.io/blob/main/docs/faq.md): describes guest URL opening via its link UI.

Native sign-in now redirects Supabase to **`https://internos-green.vercel.app/auth/native/return?state=…`**. This HTTPS relay presents an explicit Open in LiveContainer button, secondary-instance options, and an ordinary directly installed app option. It constructs only the source-verified `livecontainer://open-url?url=BASE64(original-callback)` form (or the selected supported instance). The decoded callback remains `com.internos.mobile://auth/callback?state=…&code=…`. It does not guess a guest bundle-folder name or auto-select a host. Keep the originating guest running in the same instance.

The relay passes the original one-use PKCE authorization code and nonce. It does not exchange that code, authenticate in Safari, obtain session tokens, copy cookies, or inject sessions. The original WebView must match its three-minute host-only HttpOnly flow cookie and PKCE verifier, POST the strict callback contract to the existing same-origin endpoint, exchange the code once, and verify its user/session before navigation. Replays, missing/mismatched state/verifier, external destinations, duplicated parameters, and session-token fragments are rejected. Invalid relay requests have a clear error page; native cancellation/expiry explains retrying and selecting the proper host. The relay is no-store, no-referrer, script-free, frame-blocked, and loads no external resources. Ordinary web Google sign-in continues through `/auth/callback`.

No native files or plugins changed. An IPA rebuild is **not required** for these hosted web changes; no IPA output exists for this task. A temporary simulator-only `.app` was compiled at `/tmp/internos-simulator-validation/Build/Products/Debug-iphonesimulator/App.app` to inspect registration. The simulator accepted opening the synthetic callback and displayed the iOS “Open in InternOS?” prompt. This verifies scheme registration only; it does not verify Google authentication or a LiveContainer guest callback. Full physical-device and simulator Google sign-in remain unverified. LiveContainer 3.8.0 compatibility must be confirmed on the actual installation.
